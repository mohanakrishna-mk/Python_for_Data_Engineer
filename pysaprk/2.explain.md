# 1. Create SparkSession

```python
spark = (
    SparkSession.builder
    .appName("SparkConcepts")
    .master("local[*]")
    .config("spark.sql.shuffle.partitions", "4")
    .getOrCreate()
)
```

### Concepts

**SparkSession**

Entry point to Spark SQL/DataFrame operations.

```text
Your Python code
      ↓
SparkSession
      ↓
Spark
```

### `.master("local[*]")`

For local practice.

`*` means Spark can use the available local CPU cores.

In a real cluster, you normally don't specify this in the application code; the cluster manager handles resource allocation.

### `spark.sql.shuffle.partitions = 4`

This is important later.

When Spark performs certain shuffle operations, such as:

```python
groupBy()
join()
```

Spark needs shuffle partitions.

Here we're telling Spark to initially use **4 shuffle partitions**.

# 2. Read the data

```python
sales = spark.read \
    .option("header", True) \
    .option("inferSchema", True) \
    .csv("sales.csv")
```

### Concepts

### DataFrame

`sales` is a Spark DataFrame.

Think:

```text
sales
 ↓
Distributed table
 ↓
multiple partitions
```

For example:

```text
sales
│
├── Partition 0
├── Partition 1
├── Partition 2
└── Partition 3
```

But **nothing necessarily gets processed immediately**.

This introduces:

### Lazy evaluation

Spark doesn't immediately execute the whole computation just because you called `read` or transformations.

Spark builds a plan.

# 4. Filter

```python
filtered = (
    sales
    .filter(col("amount") > 100)
    .select("customer_id", "city", "amount")
)
```

This section introduces several concepts.

---

## `.filter()`

```python
.filter(col("amount") > 100)
```

This is a **transformation**.

More specifically, it is generally a:

### Narrow transformation

Why?

Suppose:

```text
Partition 0 → filter → Partition 0
Partition 1 → filter → Partition 1
Partition 2 → filter → Partition 2
Partition 3 → filter → Partition 3
```

Each partition can be filtered independently.

No need to move data between partitions.

So:

```text
filter()
   ↓
Transformation
   ↓
Narrow
   ↓
No shuffle normally
```

---

# 5. Select

```python
.select("customer_id", "city", "amount")
```

Also a transformation.

It selects columns.

Generally narrow:

```text
Partition 0 → select → Partition 0
Partition 1 → select → Partition 1
```

Again, no need to redistribute data.

---

# 6. Nothing has actually run yet

This is extremely important.

After:

```python
filtered = (
    sales
    .filter(...)
    .select(...)
)
```

you might think:

> "Spark has read the file, filtered it and selected columns."

Not necessarily.

Spark is being **lazy**.

Conceptually it has:

```text
Read
 ↓
Filter
 ↓
Select
```

as a plan.

No action has forced execution yet.

---

# 7. groupBy

Now:

```python
aggregated = (
    filtered
    .groupBy("customer_id", "city")
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("transaction_count")
    )
)
```

This is where things become more interesting.

---

## `groupBy()`

```python
.groupBy("customer_id", "city")
```

This is a **wide transformation**.

Why?

Imagine:

```text
Partition 0
customer A

Partition 1
customer A

Partition 2
customer B
```

Spark needs all records for customer A together.

So data has to move:

```text
Partition 0 ──┐
Partition 1 ──┼── SHUFFLE
Partition 2 ──┘
                  ↓
          New partitions
```

That's a:

# Shuffle

Shuffle means **redistributing data between partitions**, usually involving network/data movement in a cluster.

---

# 8. Shuffle creates a stage boundary

This is where your previous question connects.

Your code:

```python
filter()
select()
groupBy()
```

doesn't explicitly say:

```text
Stage 1
Stage 2
```

Spark figures it out.

Conceptually:

```text
Stage 0
│
├── Read
├── Filter
└── Select
       ↓
    SHUFFLE
       ↓
Stage 1
│
├── GroupBy
├── Sum
└── Count
```

So:

```text
Narrow transformations
       ↓
    Stage 0
       ↓
    Shuffle
       ↓
    Stage 1
```

This is why understanding shuffle is so important.

---

# 9. `.agg()`

```python
.agg(
    sum("amount"),
    count("*")
)
```

This performs aggregation.

Spark may use aggregation mechanisms internally such as hash aggregation.

Conceptually:

```text
Group by customer
      ↓
Calculate sum
      ↓
Calculate count
```

This happens after the required shuffle.

# 10. Join

Now:

result = aggregated.join(

### Join

You're combining:

```text
aggregated

```

# 11. Broadcast

This part:

```python
broadcast(customers)
```

is particularly important.

Suppose:

```text
aggregated = 500 GB
customers = 10 MB
```

Instead of shuffling the huge dataset to perform the join, Spark can broadcast the small dataset to executors.

Conceptually:

```text
             customers
                ↓
       ┌────────┼────────┐
       ↓        ↓        ↓
   Executor  Executor  Executor
       │        │        │
       └──── aggregated ┘
```

This can avoid a large shuffle associated with the small side.

**Important:** broadcasting isn't automatically good for every dataset. The broadcast side needs to be small enough for executor memory.

---

# 12. Cache

```python
result.cache()
```

This tells Spark:

> "I may use this result again, so keep it in memory/storage if possible."

But there's an important detail:

```python
result.cache()
```

does **not immediately calculate and cache everything**.

It's still lazy.

The cache becomes populated when an action runs.

For example:

```python
result.cache()

result.show()     # execution + cache population
result.count()    # can reuse cached result
```

---

# 13. `show()` — Action

```python
result.show()
```

Now we finally have an **action**.

This forces Spark to execute the required plan.

This is where:

```text
Transformation
       ↓
Lazy plan
       ↓
ACTION
       ↓
JOB
```

So:

```python
result.show()
```

can trigger a Spark job.

---

# 14. Job

Conceptually:

```text
show()
 ↓
JOB 1
```

The job contains the stages necessary to produce the requested result.

For example:

```text
JOB 1
│
├── Stage 0
│    Read
│    Filter
│    Select
│
│       ↓ Shuffle
│
├── Stage 1
│    GroupBy
│    Aggregate
│
│       ↓
│
└── Stage 2
     Join
```

The exact number and arrangement of stages depends on Spark's physical execution plan and join strategy.

---

# 15. Tasks

Suppose Stage 0 has 4 input partitions.

Spark can create:

```text
Stage 0
│
├── Task 0 → Partition 0
├── Task 1 → Partition 1
├── Task 2 → Partition 2
└── Task 3 → Partition 3
```

A **task** is essentially the unit of work Spark schedules for a partition within a stage.

So:

```text
JOB
 ↓
STAGE
 ↓
TASK
 ↓
PARTITION
```

---

# 16. Executors

Where do those tasks run?

On **executors**.

Conceptually:

```text
Driver
  │
  ├── Executor 1
  │     ├── Task 0
  │     └── Task 1
  │
  └── Executor 2
        ├── Task 2
        └── Task 3
```

### Driver

Coordinates the application.

### Executor

Runs tasks and stores cached/shuffle-related data.

window = (

### One correction to keep in mind

Don't think:

> `groupBy()` = Stage.

Instead think:

> `groupBy()` **can require a shuffle**, and the shuffle creates a **stage boundary**.

Similarly:

> `filter()` doesn't automatically mean "Stage 0." Spark's physical planner determines how operations are grouped into stages.

That's the key mental model that will prevent confusion when you start looking at the **Spark UI**.
