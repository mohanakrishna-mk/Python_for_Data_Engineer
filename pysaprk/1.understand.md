Yes — that's actually a **better way to learn**. We can use **2 PySpark programs** that together demonstrate almost all important Spark concepts.

## Code 1 — Core Spark concepts

This single program covers:

**DataFrame → transformations → actions → lazy evaluation → partitions → narrow/wide → shuffle → job → stages → tasks → aggregation → joins → caching → DAG**

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, sum, count, broadcast
from pyspark.sql.window import Window
from pyspark.sql.functions import row_number

spark = (
    SparkSession.builder
    .appName("SparkConcepts")
    .master("local[*]")
    .config("spark.sql.shuffle.partitions", "4")
    .getOrCreate()
)

# --------------------------------------------------
# 1. READ DATA
# --------------------------------------------------

sales = spark.read.option("header", True).option(
    "inferSchema", True
).csv("sales.csv")

customers = spark.read.option("header", True).option(
    "inferSchema", True
).csv("customers.csv")

print("Partitions:", sales.rdd.getNumPartitions())

# --------------------------------------------------
# 2. NARROW TRANSFORMATIONS
# --------------------------------------------------

filtered = (
    sales
    .filter(col("amount") > 100)
    .select("customer_id", "city", "amount")
)

# Nothing executed yet!
# Spark is building the logical plan.

# --------------------------------------------------
# 3. WIDE TRANSFORMATION / SHUFFLE
# --------------------------------------------------

aggregated = (
    filtered
    .groupBy("customer_id", "city")
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("transaction_count")
    )
)

# groupBy can cause SHUFFLE.
# This can create a stage boundary.

# --------------------------------------------------
# 4. JOIN
# --------------------------------------------------

result = aggregated.join(
    broadcast(customers),
    "customer_id",
    "left"
)

# broadcast() can avoid a large shuffle
# when customers is small enough.

# --------------------------------------------------
# 5. CACHE
# --------------------------------------------------

result.cache()

# --------------------------------------------------
# 6. ACTION → JOB
# --------------------------------------------------

result.show()

# show() triggers a Spark JOB.

# Another action can create another job:

print("Count:", result.count())

# --------------------------------------------------
# 7. WINDOW FUNCTION
# --------------------------------------------------

window = (
    Window
    .partitionBy("city")
    .orderBy(col("total_amount").desc())
)

ranked = result.withColumn(
    "rank",
    row_number().over(window)
)

ranked.show()

# --------------------------------------------------
# 8. EXPLAIN EXECUTION PLAN
# --------------------------------------------------

ranked.explain(True)

# --------------------------------------------------
# 9. WRITE
# --------------------------------------------------

ranked.write.mode("overwrite").parquet("output/")

# write() is another ACTION.

# --------------------------------------------------

result.unpersist()

spark.stop()
```

```text

│
├── DataFrame
│
├── Transformations
│    ├── filter()
│    ├── select()
```

# Code 2 — Performance concepts

The second program focuses on the concepts you'll need for **optimization/performance interviews**:

**repartition → coalesce → skew → shuffle → partition pruning → predicate pushdown → AQE → file formats → Spark UI**

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, rand

spark = (
    SparkSession.builder
    .appName("SparkPerformance")
    .master("local[*]")
    .config("spark.sql.shuffle.partitions", "8")
    .config("spark.sql.adaptive.enabled", "true")
    .getOrCreate()
)

# --------------------------------------------------
# 1. READ PARQUET
# --------------------------------------------------

df = spark.read.parquet("sales_parquet/")

# Parquet supports:
# - Column pruning
# - Predicate pushdown
# - Compression
# - Schema

# --------------------------------------------------
# 2. PARTITION PRUNING
# --------------------------------------------------

df_2026 = df.filter(col("year") == 2026)

# If files are partitioned like:
#
# sales/
#   year=2025/
#   year=2026/
#   year=2027/
#
# Spark can potentially read only year=2026.

# --------------------------------------------------
# 3. PREDICATE PUSH DOWN
# --------------------------------------------------

filtered = df_2026.filter(
    col("amount") > 1000
)

# Spark can push this filter closer
# to the Parquet scan.

# --------------------------------------------------
# 4. REPARTITION
# --------------------------------------------------

repartitioned = filtered.repartition(
    8,
    "customer_id"
)

# Redistributes data.
# Usually causes SHUFFLE.

# --------------------------------------------------
# 5. AGGREGATION
# --------------------------------------------------

summary = (
    repartitioned
    .groupBy("customer_id")
    .sum("amount")
)

# Another possible shuffle.

# --------------------------------------------------
# 6. DATA SKEW EXAMPLE
# --------------------------------------------------

skewed = df.select(
    col("customer_id"),
    col("amount")
)

# Imagine:
#
# customer A → 90% of records
# customer B → 2%
# customer C → 2%
# customer D → 2%
# customer E → 2%
#
# One task can become much slower.

# --------------------------------------------------
# 7. COALESCE
# --------------------------------------------------

small_output = summary.coalesce(2)

# Reduces partitions.
# Usually avoids a full shuffle.

# --------------------------------------------------
# 8. EXPLAIN
# --------------------------------------------------

small_output.explain(True)

# Look for things such as:
#
# Exchange
# Sort
# HashAggregate
# FileScan
#
# Exchange commonly indicates shuffle.

# --------------------------------------------------
# 9. ACTION
# --------------------------------------------------

small_output.show()

# ACTION → JOB
#
# JOB
# ├── STAGE
# │    ├── TASK
# │    ├── TASK
# │    └── TASK
# │
# └── STAGE
#      ├── TASK
#      ├── TASK
#      └── TASK

# --------------------------------------------------
# 10. WRITE
# --------------------------------------------------

small_output.write.mode(
    "overwrite"
).parquet("optimized_output/")

spark.stop()
```

## The mental model you should remember

When you run either program:

```text
             YOUR PYSPARK CODE
                    ↓
             Transformations
                    ↓
             Lazy DAG / Plan
                    ↓
                ACTION
                    ↓
                  JOB
                    ↓
          ┌─────────┴─────────┐
          ↓                   ↓
       STAGE 0             STAGE 1
          ↓                   ↓
       TASKS                TASKS
          ↓                   ↓
      EXECUTORS           EXECUTORS
          ↓
       SHUFFLE
```

And the most important connection is:

```text
groupBy / join / orderBy
          ↓
       SHUFFLE
          ↓
   STAGE BOUNDARY
          ↓
   MORE TASKS
          ↓
   MORE DATA MOVEMENT
          ↓
   POTENTIAL PERFORMANCE ISSUE
```

If you understand these **two programs + Spark UI**, you'll have a much stronger foundation than simply memorizing individual Spark definitions.
